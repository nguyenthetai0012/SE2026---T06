## Reproduce from the repository root

Use Python 3.10+ with the standard-library sqlite3 module:

```text
python tests/integration/verify_event_ingestion_prototype.py
python tests/integration/verify_event_refactor.py
```

For a functional check that does not repeat the 291-thread burst:

```text
python tests/integration/verify_event_ingestion_prototype.py --functional-only
```

Fresh results, candidate source and isolated SQLite databases are created under `work/ad022-evidence/`. They do not overwrite these recorded results. Do not commit generated databases or runtime files.

## Observed results and limits

- T01-T07 pass their scoped assertions. T08 is the earlier one-use-helper characterization, kept for provenance; it is not the final refactor design.
- T09 preserves the same outcomes for 11 operations and the same persisted row, covering each content field's conflict handling, validation and storage failure.
- F01 reproduces stale replay being accepted after purge. F02 reproduces a raw OperationalError from purge on an uninitialized database. These are unresolved application defects, not evidence that the system is ready.
- The original simultaneous burst submitted 291 unique events through 291 threads to one local SQLite database: 26 accepted, 265 EventStoreUnavailable, p95 terminal latency 3.4999 seconds and p95 successful latency 3.5277 seconds. Timing excludes the barrier wait. Rates/timings will vary on another machine or run.
- This measures one local ingestion burst, not sustained users, MQTT/HTTP, dashboard queries or end-to-end recovery. The 291-user/API p95 target is not validated. The measured burst did not meet 2.5 seconds and had a high error rate.
- T07's snapshot/JSONL replay is harness-only with three events. It does not establish production RTO/RPO or implement recovery in C1.
